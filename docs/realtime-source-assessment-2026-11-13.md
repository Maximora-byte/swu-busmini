# 实时车辆数据接入评估

2026-11-13，对用户本地已解包的享坐车客户端进行只读静态分析。用户确认其车辆数据准确；本次没有连接推送服务、读取认证值、采集实时车辆或用户位置，也没有部署代理。以下描述是客户端实现证据，不能证明当前服务允许第三方匿名订阅、长期可用或已授权再分发。

## 结论

车辆位置可以用于本项目的地图叠加层。现有 `VehicleLocationProvider` 能容纳基本车辆快照，但直接复制原客户端连接逻辑会同时引入账号上下文、位置上报和其他数据类别。接入前需要取得允许第三方使用的只读车辆订阅方式，或由有权访问数据的服务提供经过筛选的车辆接口。静态公交导航可继续独立使用；此次没有启用实时功能。

## 客户端证据

| 通道 | 与车辆相关的内容 | 对本项目的影响 |
| --- | --- | --- |
| WebSocket 车辆消息 | 按学校过滤，包含车辆、线路、经纬度、速度、航向及状态；消费端记录本地接收时间 | 可转换为车辆快照；本地收到消息的时间不能代替原始 GPS 采样时间 |
| WebSocket 请求 | 初始请求带用户上下文，随后约每五秒的请求包含用户坐标；另有邻近站点上报 | 不能照搬请求与定时器。实时地图不需要上传乘客坐标或调用候车请求 |
| 同连接的其他消息 | 还支持用户位置类别和管理相关请求 | 必须在数据源边界排除；仅在页面不显示这些数据仍不足以证明没有接收 |
| MQTT 辅助站时消息 | 可包含业务方向、GPS 时间、更新时间、当前站序和平均速度；订阅依赖运行时登录配置 | 不应提取或把客户端认证值放入本项目；站序和线路必须单独映射、校验 |
| 连接生命周期 | 有心跳、重连及前后台断开／恢复逻辑；辅助站时缓存包含过期控制 | 本项目还需明确断线、过期和重连状态，不能让最后一次车辆位置持续显示为实时 |

WebSocket 连接调用本身未显式设置认证字段，不等于服务无认证或允许匿名使用。现有客户端未展示独立的“仅车辆”订阅开关。两条通道中的 `direction` 含义也不同：车辆地图使用航向角，辅助站时使用业务方向枚举，不能共用同一个字段解释。

## 可用的接入边界

1. 先确认数据使用及再分发权限、车辆专用订阅协议、学校／线路范围、坐标系、原始采样时间、更新频率及服务限制。校园静态坐标目前按 GCJ-02 使用，实时坐标仍需数据方确认。
2. 若接口需要持久凭证，在服务端保存并接入。对小程序只提供经过筛选的校内车辆字段，不能把原客户端账号配置、认证值、请求身份或任意消息转发给前端。
3. 将来源线路映射到本项目线路 ID，车辆使用本项目内部 ID；未知线路、非法坐标、过期或顺序倒退的数据拒收。上游信息不能覆盖静态站序或证明目前尚未确认的环线运营方向。
4. 将采样时间和接收时间分开；无可靠采样时间时明确说明。车辆状态需要区分新鲜、过期、不可用，断线后清除或标记旧点，不承诺未经验证的到站时间。
5. 默认关闭实时层，静态规划不等待网络；启用后只显示车辆信息，不上报用户位置、不触发叫车／近站上报、不订阅用户专属或管理主题。前后台切换和卸载均释放连接、定时器及监听。

这是待落实的接入条件，不代表上述适配、服务或后台已经实现。当前接口 `VehicleLocationProvider.getVehicles()` 尚无实现，现有 `Vehicle.updatedAt` 一个时间字段也不足以表达全部新鲜度状态。

## 发布与验证范围

公开文档只保留协议类别、字段含义及设计限制；不含接口地址、来源学校／线路／车辆标识、账号、认证值、个人位置或本机路径。详细静态代码定位和本地测试材料独立保留。

后续接入应以合成消息测试字段白名单、线路映射、坐标范围、乱序、过期、断线重连和前后台恢复，再在获准的数据源上验证。完成前不能把车辆叠加、到站预测或真实运营方向标记为已验收。
